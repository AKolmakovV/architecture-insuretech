## Решение:

1. Доработанная схема: ["InsureTech-C4Digram-Container-to_be.drawio"](./InsureTech-C4Digram-Container-to_be.drawio)
2. Свое хранилище требуется, в нем будут храниться список заявок со статусами, в случае сбоя, сервер запустится, и продолжит опрашивать страховые компании по заявкам, которым нет статуса от страховых, а также внутренний статус - обработано, значит сообщение было отправлено в шину, также это решит проблему, когда был перезапуск например core-app и заявка отправлена заново, если по ней уже есть решение, ответ придет моментально
3. API core-app - osago-aggregator:

Так как мы работаем через брокер сообщений, у нас будут не API а сообщения(события), выделим следующие типы:

- Запустить расчет заявки 
- Сформировано решение по заявке

4. В качестве средсва интеграции мы будем использовать брокер сообщений и подписку-публикацию для сервисов core-app и osago-aggregator
5. Применяемые паттерны:
   1. Rate Limiting - для сервисов взаимодействующих с платными сервисами (при условии что сервисы страховых компаний платные) - так мы защитим себя от перерасхода средств, и даем возможность отреагировать на проблему путем оптимизации взаимодействий с данными сервисами
   2. TimeOut - для ограничении времени запрос - ответ, для работы с внешними сервисами, иначе мы можем тратить системные ресурсы впустую, на подвисших запросах
6. Готово, на схеме: ["InsureTech-C4Digram-Container-to_be.drawio"](./InsureTech-C4Digram-Container-to_be.drawio)
7. Решение защищено, мы работаем только с теми заявками, которые были зарегистрированы в базе данных сервисов, например osago-aggregator-db, в единичном экземпляре
